# PRD: Aluna Desktop — the capability surface

Status: needs-triage

## Module

Aluna Desktop — the product surface on which capabilities are presented.

**Module placement is not settled and this PRD does not settle it.** The work was
scoped as "the new fifth module, starting once Module 4 is done", but
`docs/modules.md` already assigns Module 5 to *Reads Set Free: Ad-hoc Data
Queries*. Renumbering the existing plan is a maintainer decision, so this PRD
lives in `docs/prd/` until the slot is chosen. Once it is, the file moves to
`modules/<module-slug>/` and is broken into epics and issues.

## Problem Statement

Aluna's current shell works and is lifeless. Capabilities are regions of one
page: they appear in a sidebar, they render into a content column, and nothing
about the presentation says that these are *things Aluna grew*. A product whose
entire premise is self-evolution presents its evolution as a list.

The runtime is not the problem. Filesystem, unit generation, snapshots,
manifests, the design contract and its Gate, and the prompt bar are all correct
and stay exactly as they are. What is missing is a surface where a new
capability arrives as a visible, addressable, first-class object — and where the
act of growing one is something the user watches happen rather than something
they infer from a sidebar gaining a row.

The current visual language is also the wrong register. Subtler neobrutalism on
Paper & Ink reads as a well-made developer tool. Aluna is not a developer tool.

## Solution

Aluna's product surface becomes a **desktop**, and every capability becomes an
**app** on it: an icon on the ground, a window when opened, a life cycle you can
see. Windows float, overlap, and are dragged. There is no taskbar. The prompt
bar floats above the desk and is the only thing on screen that belongs to Aluna
rather than to a capability.

The visual register is **retro solarpunk in the ligne claire method** — flat
fills at high chroma, one warm near-black used only for lines and type, hard
offset shadows, no gradients and no blur. The reference standard is the art
direction of *Sable*, *Terra Nil* and *Europa*; the product reference is
Poolsuite. The register is explicitly artist rather than engineer: **no
monospace, no terminal vocabulary, no boot sequence.**

D10 pulls that register somewhat toward **drafting** — square corners, one uniform
weight, no texture, a rule crossing its frame is closer to a plan sheet than to a
comic page. This is accepted. The consequence is that the warmth now has to arrive
somewhere other than the chrome: the wallpaper, the icon marks and the title-bar
panes carry all of it, and those are the parts Aluna designs rather than the parts
we do. If the surface ever reads cold, that is the place to look, not the line.

Nothing below changes what a capability generates. The one place this work
reaches into the generation contract is the icon: Aluna must emit two band
colours and a mark per capability. That is the entire addition.

## Locked design decisions

These are settled. They are stated here as constraints for implementation, not
as options.

| # | Decision |
| --- | --- |
| D1 | **Free-floating windows.** Windows overlap and are dragged freely. On mobile, one capability fills the screen and the desk reads as a phone home screen. |
| D2 | **Singleton.** One window per capability. Opening an already-open capability focuses its existing window. |
| D3 | **Close means put away.** The window disappears; nothing in storage changes. Retiring a capability stays a separate, explicit, confirmation-gated action. |
| D4 | **Desktop icons only.** No taskbar. Capabilities live on the ground as icons. |
| D5 | **Prompt bar always visible**, floating above the desk. |
| D6 | **Seed-to-icon is the arrival animation** for a newly grown capability. The detailed choreography is future work. |
| D7 | **Fast, multi-window, interactive.** PostHog's desktop site is the concept, not the performance bar. |
| D8 | **Accessibility is best-effort**, not a release gate. |
| D9 | **A table stores desk layout.** Window position, size, z-order and open state persist. Icons are generated by Aluna. |
| D10 | **The line is drawn, not ruled.** Every window edge is mitred, deviates 0.9px from true, and is inked twice. Full specification under *The window*. |

### Consequences that bind implementation

- D4 makes the icon load-bearing: it is the capability's permanent identity
  **and** the minimise destination. A window minimises back into its own icon.
- D3 means every title-bar control is reversible. No destructive affordance
  appears in window chrome.
- D9's layout table sits outside the capability's own schema, so window
  coordinates never travel with an evolution candidate.
- D10 puts a per-window **seed** in D9's layout table. The seed is what makes one
  window's hand differ from the next, and it must persist: derive it from position
  or size and the frame visibly re-rolls the moment a window is dragged.
- D10 also forces a corner vocabulary split. Windows are mitred; the icon tile
  keeps its 16px radius, because a 64px tile has no room for the treatment and
  does not need it.

## The visual method

Read off the reference frames and applied everywhere.

1. **Flat fills at high chroma.** No shading. Depth comes from ordered bands —
   light in front, dark behind — never from gradients or shadows.
2. **One ink, for lines and type only.** `#20301C` at 2px hairline weight around
   shapes. It is never a background, never a card, never a fill. Any large dark
   shape is a saturated hue instead.
3. **Hard offset shadows.** Displacement, never blur.
4. **Light only.** There is no dark theme. This palette is daylight and does not
   invert. The viewer's OS dark preference is deliberately ignored.
5. **The line is hand-made in its path, uniform in its weight.** Classical ligne
   claire holds one nib weight everywhere and refuses hatching; what it does not
   hold is a perfectly true route, because a hand drew it. So the deviation is in
   *where the line goes*, never in how thick it is, and never a taper inside a
   single stroke. Weight variation, where it reads at all, comes only from a
   second inking pass laid slightly off the first.
6. **No texture, anywhere.** No screens, hatching, grain, stipple or
   misregistration on any surface. Every fill is flat and unmodulated. This was
   tested across thirteen candidates and rejected as a set.

Muted colour is a function of area, not taste: colour covering a large area is
held back, colour occupying a small area runs at full strength.

## The window

Settled. A square window, inked twice, with one line that does not stop at the
frame.

| Part | Specification |
| --- | --- |
| Frame | 2px `ink`, **mitred — 0px radius**, `surface` fill, no inner stroke |
| Line | Every stroke inked **twice**. Second pass offset `+0.7px` across, `+0.56px` down, at **74% ink each**, carrying its own seed — a genuine re-inking, not a translated copy of the first |
| Deviation | The path deviates **0.9px** from true on a **58px** wavelength, seeded per window. Smooth, low-frequency, periodic. A **constant** — never scaled with window size |
| Weight | **Every line 2px.** No weight hierarchy by role, anywhere |
| Title-bar rule | 2px, **runs through the frame 5px each side**, not clipped. `×1.15` reach on the second pass |
| Shadow | `5px 6px 0` ink at 24% — hard offset, never blurred |
| Title bar | `surface` from 0–50%, then five panes at 10% each: `#F7E4BC` · `#F5D4BC` · `#CFE8C6` · `#C6E7E2` · `#C9EAF1`. Hard cuts, vertical edges |
| Title | Fraunces 700, 20px, `SOFT 80 · WONK 1 · opsz 60`, ink. Sits bare on the chrome — **no lozenge, plate or badge** |
| Lamps | 12px circles, 2px ink stroke — sun, leaf, clay for minimise, maximise, put away. All reversible; none is signal red |
| Unfocused | Title bar desaturated to 50%. Frame, lamps and content unchanged |
| Body | `surface`, flat. **No texture.** The chrome never reaches into generated content |

Over a wallpaper rather than flat colour, windows and the floating prompt bar
carry their shadow at **40%** rather than 24%.

The prompt bar takes the same line treatment — twice-inked, same deviation — but
stays a **rounded rail**. The mitre is a decision about windows.

**Why the title-bar rule runs through**, recorded so it is not relitigated: in a
square, twice-inked, textureless window where every line is the same weight, that
rule breaking the frame is the only mark on screen that is not structural. It
reads as deliberate precisely because it is the only one. An earlier candidate ran
the same crossing at all four corners as well; four crossing corners plus a
crossing divider is a system of crossings, and one crossing is a signature.

**Why hard cuts rather than a gradient**, recorded so it is not relitigated: the
cuts are the same logic as the icon's stacked bands and the reference frames'
landforms, where ordered flat fills *are* the depth model. One soft edge in a
system with none would read as the rule slipping. Cuts also leave a door open a
gradient closes — five discrete cells can each be lit independently if the bar
should ever carry live state.

### Drawing the frame

Four rules that matter more than the implementation does.

| Rule | Why |
| --- | --- |
| The noise is smooth and periodic | Per-point randomness is sandpaper. The deviation has to be low-frequency value noise that meets itself at the seam, or the frame reads as corroded rather than as drawn. |
| The seed lives on the window | Stored in D9's layout table, never derived from position or size. If the seed moves, a re-render mid-drag re-rolls the hand and the frame visibly twitches. |
| Regenerate on resize only | Dragging is a CSS transform. Only a size change invalidates the path. This is what keeps D7's performance bar cheap. |
| Corners must be pinned | A spline through a corner rounds it. Repeat the corner point so the tangents collapse, or "mitred" quietly becomes a 3px radius. |

Ten stroke paths per window: four edges plus the title-bar rule, twice. The fill
silhouette is a closed ring over the same four edges.

## The icon contract

**Aluna designs these; we do not.** We own the frame they arrive in and the
rules they must satisfy. Everything inside is the product's creative surface.

### The shell owns — fixed, identical on every icon

- 64px rounded square, 16px radius, 3px ink stroke
- Sky band across the top, always `#C4EBF1`
- The **double band** below it, on fixed horizon curves — back band then front
  band. Never one band, never three
- The label beneath, in Outfit, **on a plate**: a small `surface` pill with a
  1.5px ink hairline and a 999px radius. The plate is not optional — bare label
  text is legible on flat colour and illegible over a wallpaper, and the desk
  always has one

**The icon is not affected by D10.** It keeps its 16px tile radius, its closed
corner, and a single true stroke. A 64px tile has no room for a 0.9px deviation
or a second inking pass — at that scale the deviation is proportionally three
times louder and the tile reads as damaged rather than drawn. The desk therefore
carries two corner vocabularies on screen at once: mitred windows, rounded tiles.
That is accepted, on the grounds that a tile and a window are different objects.

### Aluna owns — free within bounds

- **Both band colours**
- **The mark** — any shape it likes

#### Band colour — guidance

| Rule | Bound |
| --- | --- |
| Start from the anchors | The eight named tints are the defaults. Going outside them is allowed when a capability genuinely calls for it — bounded freedom, not a closed set. |
| Stay in the family | Saturated and light enough to sit in daylight: broadly the chroma and lightness range the anchors occupy. No near-blacks, no pastels, no greys. |
| Back band is the front band, deepened | Same hue, darkened toward ink by roughly a third. Two unrelated colours break the landform reading — this is one slope in light and shade, not two stripes. |
| Never signal red | `#D6304B` and its near neighbours are reserved. |
| Distinct from neighbours | Where possible, not the same hue as the capability created immediately before it — the desk is read by colour first. |

#### The mark — parameters

| Parameter | Value |
| --- | --- |
| Size | Fits a 32×32 box within the 64px tile — half the tile, no more. Centred horizontally, seated on the horizon rather than floating in the sky band. |
| Stroke | **2.5px ink outline, mandatory**, on every shape including open paths. This is what guarantees contrast against any band colour without testing each pairing. |
| Fill | Surface white, or none. No third colour inside the mark. |
| Open paths | Drawn twice — ink at 5.5px beneath, surface at 2.5px on top — producing the same outlined result on a shape with no fill. |
| Legibility | Must hold at 32px. In practice a handful of strokes, not an illustration. |
| Subject | **Free.** Aluna's call, deliberately unconstrained. |

### The trade this accepts

Every desk will be genuinely different, and some marks will land badly. The
mandatory stroke and the 32px legibility bound are what keep a weak mark merely
dull rather than broken — nothing can produce an invisible or shapeless icon
inside these parameters. If a capability's mark turns out poor, the fix is
regeneration, not a fallback library.

## Capability presentation patterns

Shell-level patterns applied to every capability, not decisions generation makes.

### The collection header

| Row | Contents | Why |
| --- | --- | --- |
| 1 · Search | Full-width pill input with a magnifier, placeholder naming the thing — "Search customers…" | The first thing you want on any collection of unknown size, and full width means it never competes for the row. |
| 2 · Count & action | Record count left in small caps; the primary "New record" button right. | The count answers "how much is here" before you scroll, and pairing it with the create action puts the two collection-level facts on one line. |
| 3 · Records | The feed or grid, per the capability's declared layout. | Unchanged from what exists today. |

The count is **live** and updates on search — a filtered count is more useful
than a total, and it doubles as the search's own feedback without needing a
separate status line.

**Row 1's pill is unresolved against D10.** A square frame raises the question of
what happens to everything inside it, and squaring the search input contradicts
this row as written — as squaring the icon's label plate would contradict the icon
contract. Open Question 1 carries the decision; until it is called, both locked
lines stand and components stay rounded.

### The record form

Field label in small caps above its control, guidance text below in subtle ink,
related short fields paired two-up, and an actions row separated by a rule —
save and cancel on the left, **destructive isolated on the right**. That
separation keeps D3 honest at the record level too: destructive actions are
never adjacent to routine ones.

## The desk

- **The ground** carries a wallpaper. Direction is settled — flat vivid fills,
  hairline ink, a landscape with a horizon — but the artwork does not exist yet
  and is not designed in this PRD.
- **Icons** sit on the ground in a grid. The grid is the same surface at desktop
  and phone sizes, per D1.
- **Icon labels sit on a plate**, per the icon contract above.
- **The prompt bar floats**: a rounded rail clear of all four edges with ground
  visible beneath and beside it. It is never a full-width bottom bar — a bar
  welded to the bottom edge *is* a taskbar, which D4 removed. It holds position
  when windows move behind it, and windows pass under it.

## User Stories

1. **As a user opening Aluna**, I see a desk with an icon for every capability I
   have, so what Aluna has built for me is visible before I do anything.
2. **As a user**, I click a capability's icon and its window opens, so the thing
   I clicked and the thing that opened are visibly the same object.
3. **As a user with several capabilities open**, I drag windows freely and they
   overlap, so I can arrange my own workspace and compare two capabilities side
   by side.
4. **As a user**, I close a window and the capability is still on my desk, so I
   never fear that tidying up destroyed something.
5. **As a user who just asked Aluna to build something**, I watch it arrive on
   the desk as a new icon, so self-evolution is something I saw rather than
   something I was told about.
6. **As a user returning later**, my desk is arranged the way I left it.
7. **As a user on a phone**, the desk reads as a home screen and a capability
   fills the screen when opened.

## Acceptance Criteria

1. Every capability renders as a 64px icon following the shell-owned geometry:
   rounded square, 16px radius, 3px ink stroke, constant sky band, double ground
   band on fixed horizon curves, and its label beneath on a `surface` pill with
   a 1.5px ink hairline.
2. Aluna emits, per capability, two band colours and one mark; the shell draws
   everything else. No mark renders without its 2.5px ink outline.
3. Window chrome matches the specification table exactly, including the five
   named pane values and the bare 20px Fraunces title.
4. Every window frame is **mitred at 0px radius**, deviates **0.9px** from true on
   a **58px** wavelength, and is inked **twice** — second pass offset
   `+0.7 / +0.56` at **74% ink** each, on its own seed.
5. The title-bar rule **runs through the frame 5px each side** and is not clipped.
6. Each window's seed persists in the layout table and is stable across drags. The
   frame path is regenerated on resize only, never on drag.
7. Every line in the product surface is **2px**. No line is heavier or lighter to
   signal role, and **no surface anywhere carries texture**.
8. All three window lamps perform reversible actions. No destructive action is
   reachable from window chrome.
9. Closing a window removes it from the desk surface and changes nothing in
   storage; the icon remains.
10. Opening an already-open capability focuses its window rather than creating a
    second one.
11. Minimising a window returns it to its own icon.
12. Window position, size, z-order and open state persist across sessions via the
    layout table, and that table is not part of any capability's schema.
13. The prompt bar is visible at all times, floats clear of all four edges, and is
    never full-width.
14. There is no taskbar.
15. The collection header renders search, live count, and the create action in
    the specified order for every capability with a collection.
16. No monospace font, terminal styling, or boot sequence appears anywhere in the
    product surface.
17. The surface renders in one light theme regardless of OS colour-scheme
    preference.
18. Generated capability content is unchanged: it still renders from the existing
    closed presentation vocabulary, and window chrome never reaches into it.

## Out of Scope

Explicitly unchanged by this work:

- The filesystem, unit generation, snapshots, manifests, and the resolver.
- The design contract and its Gate, and the closed presentation vocabulary
  generated markup draws from.
- Prompt bar behaviour — only its placement and appearance change.
- The existing dialog, button, form and field primitives as *components*; they
  are re-skinned into High Meadow, not redesigned. **Conditional on Open
  Question 1** — squaring them would make this a redesign rather than a re-skin,
  and would move it back in scope.
- Dark theme. Not deferred — decided against.
- The seed-to-icon choreography beyond the one-line decision in D6.
- The wallpaper artwork itself.

## Open Questions

Four. The first is a design decision and it blocks the component pass; the rest
are not.

1. **Do components follow the frame?** D10 squares the window. It does not say
   what happens to everything inside it — the search input, the buttons, the
   status chips, the icon's label plate. Squaring them is the coherent answer and
   contradicts two locked lines: the collection header's *full-width pill input*
   and the icon contract's *999px label plate*. It is also much the larger edit,
   reaching into the shared button, field and dialog primitives rather than window
   chrome. A middle position exists — keep what you type into soft, harden what
   you press and what reports state — and it leaves both locked lines intact.
   **Until this is called, components stay rounded.**
2. **The button variants against green.** Seven exist plus danger, all tuned on
   the old cream ground. They read louder on High Meadow and want re-checking as
   a set rather than one at a time. This is the same pass as Question 1 and should
   be scheduled with it.
3. **The wallpaper artwork.** Direction is settled; the image has to be made.
   Open within that: horizon high or low, whether it shifts with time of day,
   and whether it is fixed or pans.
4. **Module placement**, per the note at the top of this PRD.

## Further Notes

### The contract touchpoint

The only place this work reaches outside the shell is the icon: generation must
emit two band colours and a mark per capability. That is an addition to the
Module 3 presentation contract, which Module 4 is exercising. It is small and
concrete, but it should be landed deliberately rather than discovered during
implementation.

### Performance is a design constraint

D7 sets the bar at fast and multi-window. The existing stack is already the fast
path — server-rendered fragments over HTMX, no build step, no client-side
router, no hydration. A window manager here should be CSS transforms and a
z-index map, not a framework. Keeping it that way is as much a design constraint
as an engineering one.

D10 adds ten stroke paths per window, generated in the browser. This is cheap and
stays cheap **only** under the rule in *Drawing the frame*: the path is built on
mount and on resize, and dragging is a transform over an unchanged path. Rebuild
the geometry on every drag frame and this becomes the slowest thing on the desk.

### Reference standards

- **Poolsuite** — the product north star. Period-accurate chrome, straight-faced,
  with all personality carried by palette, content and copy. Its boot screen is
  explicitly *not* taken.
- **Sable** (Shedworks) — the visual method standard: ligne claire linework,
  ordered flat bands as the entire depth model, no shading.
- **Terra Nil**, **Europa** — painterly solarpunk colour and light; technology
  placed into a soft painted world.
- **Game UI Database** — the working reference library for interfaces that carry
  an art direction rather than a trend.

### What was rejected getting to D10

Recorded so it is not relitigated from memory. Two plate books: twenty-two border
treatments, thirteen textures, fourteen corner studies.

| Considered | Outcome |
| --- | --- |
| Surface texture — screens, hatching, contour, paper tooth, misregistration | Rejected outright, as a set. Every surface is a flat fill. |
| Weight hierarchy by role — a 3 / 2 / 1.5 / 1 ladder | Rejected. Every line is 2px. |
| Overshoot corners — edges crossing past each other | Explored at length, then rejected for the mitre. The crossing survives only in the title-bar rule. |
| Rounded 10px corner — the PRD's original value | Rejected for the mitre. |
| A single ink pass | Rejected. The second pass is the only source of weight variation left. |
| Brush deviation, open corners, letterpress plate mark, filter-driven roughness | Rejected early. |
| Misregistered colour plate | Rejected with texture. It was the last candidate for the D6 arrival moment. |

**The known cost of dropping the ladder**, recorded rather than buried: the window
frame and a button edge are now the same 2px line, so a window never quite sits
*in front of* its contents. The second pass covers this on the frame and does
nothing for it inside. If the desk reads flat in use, that is the cause, and one
step — frame 3px, everything else 2px — is the whole fix.
