How it works

Aluna

A personal app that builds itself from what its user types.

The first build

Making something new

The desk is empty. Its user types what to keep track of and presses Make it.

Mulling

The Intent Resolver

One model call reads the sentence and a list of every capability on the desk. The list gives each capability’s name, fields and version. It holds no records.

The call returns one decision: build something new, change a capability, link two capabilities, answer a question or refuse. The desk is empty and the sentence names something to track, so the call decides to build.

Scheming

The Core Builder writes the spec

The Core Builder’s first model call writes the spec. The spec names the capability, lists its fields with their types, sets how its cards and forms look and describes its behavior in plain words.

The platform checks the spec strictly. A spec that fails ends the build. Every later model call works from the checked spec.

While the build runs, a blank tile waits on the desk. It has no name yet.

Shelving

Nothing is stored yet

The spec names four fields: Date, Description, Amount and Category.

The tile takes the name the spec chose.

The platform plans a table for these fields and tries the plan only on a scratch database. It creates the real table at the end, in the commit that makes the capability live.

Rule-writing

Tests before code

Five model calls write test cases, one for each Action: add, open, change, remove and search. Two calls run at a time.

Each call sees part of the spec and never any code. The tests are then frozen. The code written next must pass them unchanged.

Tinkering

Six units of code

Six more model calls write the code, one unit each: the item renderer, which draws each transaction’s card, and a Handler for each of the five Actions.

As each unit arrives, the platform checks it for anything generated code may never do, such as import a module. A unit that fails goes back to the model once, and a second failure ends the build.

Tests are on by default. A build that needs no rewrite then makes twelve model calls after the Resolver: one spec, five test suites and six units.

Prodding

The Gate

The Gate runs the new code on scratch databases before the platform saves any of it. Four checks run in turn: the structure, a smoke run of every Action, the card’s markup and the frozen tests.

Three of the checks can send failing code back for a repair. A check that still fails ends the build, and nothing is published.

Mending

One repair, then check again

In this build, the search Handler returns the wrong rows for one frozen case. The Gate sends the Handler back to the model with the failure, then runs the tests again.

A repair rewrites code, never a test. The smoke run and the markup check allow one repair each. The frozen tests allow one rewrite of each Handler they catch.

A build with nothing to repair skips this stage.

Polishing

Version 1 and one commit

The platform writes the code that passed the Gate to disk as version 1: a folder holding the spec, the six units, the tests and a checksum for every file. The folder never changes after that.

Then one SQLite transaction creates the Finance tracker’s table and points the capability at v1.

If the transaction fails before it commits, SQLite rolls it back and nothing goes live. The unused folder stays on disk until the next build or restart removes it.

Ta-da

Live, without a reload

After the commit, one event carries the Finance tracker into the window, where it replaces the build’s sketch. The page does not reload.

The platform asks for the logo only now, with v1 live, so a failed logo cannot fail the build. The logo appears once it is drawn.

Some weeks later

Changing what exists

The Finance tracker holds six transactions. Its user wants to tell income from expenses.

Mulling

Same Resolver, another answer

This time the list holds one capability, the Finance tracker, with its fields. The sentence asks the tracker to store one more thing, so the Resolver decides to evolve it.

Scheming

A complete new spec

As in the first build, the next model call writes a spec: a whole new one for the Finance tracker, with every old field plus Type. This spec is called the candidate.

The capability keeps its table, its records and its logo, and gains a version.

Scheming

The Diff Engine

The Diff Engine compares the live spec with the candidate and names each difference it recognizes as a typed fact.

v1, live

Fields
Date, Description, Amount, Category
Card shows
date, description, amount, category

The candidate

Fields
Date, Description, Amount, Category, Type
Card shows
date, description, amount, category, type

It finds two facts: Type is a new field, and the card now shows it. Any other difference would end the build.

Scheming

The work plan

From the two facts, the Diff Engine plans which units to write again.

Written again

  • item renderer
  • add
  • change
  • search

Copied from v1

  • open
  • remove

Type needs new add, change and search Handlers, and the item renderer needs rewriting to show it.

Open and remove are copied byte for byte from v1, with their tests. Their code never goes into a prompt.

Building v2

Only what changed

Open and remove start out finished.

Three model calls write new tests for add, change and search. Four more rewrite the units in the plan. The Gate then checks all six.

Polishing

The version swap

The platform writes v2 as a new folder beside v1. Then one transaction adds a Type column to the table and moves the Finance tracker from v1 to v2, but only if the tracker still points at v1.

v1 stays on disk unchanged. If the transaction fails, v1 is still the live version.

Ta-da

Same records, one new field

The window swaps to v2 in place and shows the same six transactions. Their Type is empty, because the column did not exist when they were saved.

Rent, the oldest transaction, opens with no Type picked. Type stays empty until someone picks Expense or Income and saves.
