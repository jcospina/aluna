How it works

Aluna

A personal app that builds itself from what its user types.

Mulling

The Intent Resolver

The sentence goes to one model call, along with every capability already on the desk: their names, fields and versions, never a record.

The call answers with one decision: build something new, change a capability, link two of them, answer a question, or refuse. The desk is empty, so this sentence starts a build.

Scheming

The Core Builder writes the spec

The Core Builder takes the job. Its first model call writes the spec: the capability’s name, its fields and their types, how its cards and forms look, and what it does, in plain words.

Every later step is written from this spec. The platform checks it strictly, and a spec that fails the check ends the build.

A blank tile lands on the desk while the build runs. It has no name yet.

Shelving

Nothing is stored yet

The spec names four fields: Date, Description, Amount and Category.

The tile takes the name the spec chose.

The platform plans a table for those fields and tries it only on a scratch database. The real table is created at the very end, in the step that makes the capability live.

Rule-writing

Tests before code

Five calls, two at a time, write test cases for the five things the app does: add, open, change, remove and search.

They are written from the spec alone, because no code exists yet, and then frozen. The code written next has to pass them, and no later step in the build may change them.

Tinkering

Six units of code

Six more calls write the code, one unit each: the card that shows one transaction, then the Handlers behind add, open, change, remove and search.

Each unit is checked on arrival against what generated code may never do, such as importing a module. One that fails goes back to the model once, and a second failure ends the build.

With the tests on, a clean build makes twelve model calls after the Resolver: one spec, five test suites and six units.

Prodding

The Gate

The Gate runs the new code on scratch databases before any of it is written to the capability’s folder. Four checks run in turn: the structure, a smoke run through every Action, the card’s markup, and the frozen tests.

The Gate fails closed. A check that still fails once its repairs are spent ends the build, and nothing is published.

Mending

One repair, then check again

Here a frozen search case finds the wrong rows. The Gate sends the search Handler back to the model with the failure, then runs the tests again.

Each check may rewrite a failing unit once at most, and none ever edits a test. This stage appears only when a check fails and the Gate tries a repair.

Polishing

Version 1 and one commit

The cleared code is written to disk as version 1: a folder with the spec, the six units and the tests, and a checksum for every file. That folder never changes again.

Then one SQLite transaction creates the Finance tracker’s table and points the tracker at v1.

If the transaction fails before it commits, SQLite rolls it back and nothing goes live. The folder stays on disk, unreferenced, until reconciliation removes it.

Ta-da

Live, without a reload

After the commit, one event carries the Finance tracker into the window, and the drawing gives way to the app. The page never reloads.

Only now, with v1 live, does the new tile ask for its logo, so a failed drawing can never fail the build. The logo appears once it is drawn.

Some weeks later

Changing what exists

The Finance tracker holds six transactions. Its owner wants to tell income from expenses.

Mulling

Same Resolver, another answer

This time the Resolver reads the sentence beside the Finance tracker’s fields. The sentence asks it to store something new, so the answer is an evolution of the Finance tracker, not a new capability.

Scheming

A complete new spec

An evolution starts with one call too. It returns a whole candidate spec for the Finance tracker, every old field included and Type added. It is never a patch.

The capability keeps its table, its records and its logo, and gains a version.

Scheming

The Diff Engine

It compares the live spec with the candidate and names each difference as a typed fact.

v1, live

Fields Date, Description, Amount, Category

Card shows date, description, amount, category

Candidate

Fields Date, Description, Amount, Category, Type

Card shows date, description, amount, category, type

Two facts: a new field, Type, and a card that shows it. A difference no fact explains would stop the run.

Written again cardaddchangesearch

Copied from v1 openremove

Building v2

Only what changed

Open and remove are drawn finished from the start. Their code is copied from v1, and so are their tests.

New tests are written for add, change and search, then the four units in the plan are written again. The Gate still checks all six together.

Polishing

The version swap

v2 is written as a new folder beside v1. One transaction then adds a Type column to the table and moves the Finance tracker from v1 to v2, but only if it still points at v1.

v1 stays on disk unchanged. If the transaction fails, v1 is still the live version.

Ta-da

Same records, one new field

The window swaps to v2 in place. The six transactions are the same rows as before, and each holds nothing in Type, because the column was added after they were saved.

Opened, the oldest shows neither Expense nor Income. No stored value is ever rewritten, so Type stays empty until someone edits it.
