How Aluna works

A new Aluna desk holds a wallpaper, a developer utility and a prompt bar that asks What would you like to keep track of? The Developer utility opens a read-only panel for watching what Aluna does. Aluna ships with no table, form or screen for books, recipes or any other kind of record.

You type track the books I read and press Make it. While the build runs, Aluna narrates what she is doing in a window on the desk. When the build finishes, a Books tile sits on the desk, and the window shows the Books collection, empty, with a button for adding a book. The build made the table behind that collection and the code that saves a book and draws its card. That code came from the model, which is the language model Aluna is set up with. Code that ships with Aluna checked it and installed it. Aluna calls what the build made a capability.

What the steps did not show

The intent resolver is the model call that works out what a sentence asks for. A provisional tile appeared on the desk as soon as it classified yours, and the Books tile replaced that placeholder once the collection was showing. Books' logo is drawn after the build.

Two kinds of code took part. Platform code ships with Aluna and is the same for every capability. The intent resolver's prompt is platform code: it asks the model to classify your sentence against the catalog, the list of capabilities on the desk. So is the builder, which asks the model for Books' spec, then its tests, then its code. So is the Gate, which checks what the model wrote before any of it goes live. Platform code also draws every collection and form. Generated code was written by the model during this build and belongs to Books alone. It is six units, each a single file: the item renderer, which draws one book's card, and a handler for each of the five Actions, which are create, read, update, delete and search.

Platform code Written by the model

The build also left a metrics row: how long each stage took, which model ran, how many tokens it used and how the build ended. Aluna is an experiment in what a model can build, and each build's metrics row is one of its measurements.

What each part is for

The platform reads the schema. Each field becomes a control on the form and a column in cap_books, Books' table. The platform adds columns of its own, such as created_at, the time a record was created. A field has one of seven types: string, number, boolean, date, datetime, choice or string[], a list of strings. The model never writes the SQL that creates or alters a table: the platform writes it, down to how each table and column name is quoted.

ui_intent tells the platform how to present the form and the collection, and tells the item renderer how the card should look and which fields it shows. noun gives the platform its word for one book in the empty state, the record count and the prompts Aluna uses when you ask about your books.

Each unit's prompt holds only the part of the spec that unit depends on. Create and update see every field. Search sees the fields it can search as text, which are strings, choices and lists. Read and delete see no fields. Every handler also sees behavior and the errors declared for it. The item renderer sees the layout, the card's direction, the fields the card shows and the design tokens it may use (named colours, sizes and spacings), with worked examples. pages is a number the card does not show, so only create and update see it.

prompt_context is written for the intent resolver, which reads it to learn what Books holds each time it classifies a later sentence. subject, ground and companion describe the logo: something to draw and two hue families, which are named groups of colours.

Checked before anything is built

The spec must match a strict format, and the platform refuses one that does not before any table or code exists. Among what it refuses: a card that shows something other than one of the fields or created_at; required fields with no declared error for create and update; a ground and companion that name the same hue family. The platform then creates the table in a throwaway in-memory database. A schema that SQLite would refuse fails there, before the real database gets a table.

One unit at a time

The model writes each unit as a whole file: the item renderer first, then the handlers for create, read, update, delete and search. The platform checks each unit against its contract: one exported function (async for a handler, synchronous for the item renderer), no imports and nothing ambient such as process. A handler may not touch raw HTTP or run SQL that changes data. It may query only Books' table and, when the spec says that handler's Action reads another capability, that capability's table. The item renderer may read only the fields the card shows. Then the platform type-checks the unit by itself. If either check fails, the model writes that unit once more with the errors in front of it, two attempts in all. The retry touches no other unit.

The behavioral tests the Gate runs are written from the spec. No step reads the generated code to learn what Books is meant to do.

The model has written six units for Books, and nothing has run them yet. The Gate stands between those units and the desk: four rungs of checks, run in order.

All four rungs will run.

The behavioral rung is switched on. The bug to plant sits in the update handler: it keeps the capital letters you typed in tags, although the spec says tags are saved in lowercase. Which rung will catch it? Plant it and run the Gate, then run it again with the behavioral rung switched off.

Tests written from the spec

A test written by reading the handler it checks will agree with whatever that handler does, mistakes included. The model that writes the behavioral tests never sees handler code. It writes them from the behavior prose, the errors each Action declares, the part of the schema that Action works with and any capabilities that Action reads. It also sees every field, but only so that it can fill in whole sample books for its tests. Books' tests were written before any handler existed and frozen then, so no handler could shape them.

When a test fails, each handler it traces to goes back to the model for one repair, and the same tests run again. If a repaired handler still fails, the build fails and nothing is published.

How a failure is traced to a handler

When a test fails on the HTML a handler returned and the item renderer is new too, as it is on every first build, the fault could lie in the renderer as easily as in the handler. Aluna does not try to narrow it down: every handler goes back. The model repairs only handlers, so a fault in the renderer itself is still there when the tests run again, and the build fails. A test that fails before its handler runs sends no handler back, and the build fails. Smoke and design lint have repair rounds of their own; a structural failure has none.

Throwaway data

Smoke gets a fresh in-memory SQLite database for each attempt, and each behavioral test case gets its own. Each is built from the spec's schema and holds no real record for a handler to reach. Generated code runs in the same process as the platform, and in the Gate it can query and write only through what the platform hands it, built over its throwaway database. On a first build, smoke and the behavioral tests also compare every capability table in the real database before and after they run, and the Gate fails if any of them changed.

The design contract

The item renderer decides how a book's card looks. Design lint holds it to Aluna's design contract.

Chosen from design tokens

Colour, size and spacing. The model picks among named values that ship with Aluna, and each capability can still have a look of its own.

Never declared

Font family, border, corner radius and shadow. The platform sets the typeface and draws every border itself. There is no radius token, and nothing inside a window casts a shadow.

The prompt also rules out outlines and text shadows, which would draw a border or a shadow another way. It rules out transforms too, because the platform decides where a record sits. A renderer may not invent a class or nest an interactive element inside a record. It may not emit a script or an event attribute, and it may not put a field's value into a style attribute.

At runtime an enforcer drops invented classes, event attributes and any off-contract style, unwraps interactive elements and removes scripts. Design lint runs the same enforcer over synthetic and hostile values. A renderer that fails design lint is written once more, and the build fails if the rewrite is still off the contract.

What these checks cannot stop

The throwaway databases and the static checks are there to catch what a model gets wrong. They cannot contain code written to do harm: generated code runs in the same process as the platform, and Aluna has no process sandbox.

Books passed the Gate. Its spec, six units and tests will become Books' first version, v1: one directory on disk. Neither that directory nor Books' table in the real database exists yet. Files and database rows cannot change together atomically, so Aluna puts them in order: every file of the new version is written and verified first, and one SQLite transaction then makes Books live.

The commit Platform code

The transaction does three things, all or none. It creates cap_books. It adds Books to the registry, the table with one row per capability, in a row that names v1 as the live version. It marks the build's metrics row as a success. After the commit, that row cannot turn into a failure: Books is live, and only showing it is left.

A failure or a disconnect around the commit

A failure before the commit rolls the database back, and nothing goes live. A version directory already renamed into place sits unused until Aluna proves it never went live and removes it. A browser that disconnects before the commit cancels the build. A disconnect after the commit changes nothing: the build is not retried or relabelled, and a reload finds Books on the desk, because the registry lists it.

The logo, drawn later

Books is committed with no logo. Its tile asks the server for a logo attempt as soon as it lands on the desk, and the attempt waits for the build to end. One short database write claims the attempt, a separate image service draws the logo and a second write settles the result.

In the spec, the logo's subject is a stack of books, and its hue families are teal green for the ground behind the books and golden yellow for the companion colour they are drawn in. The platform assigns every capability a seed, a random number that picks one of four shades in each family, independently. The image service gets the subject, the two shades and the seed, which it uses in place of a random number of its own. The shades are worked out again from the seed on every read and never stored.

A failed attempt puts the logo back to waiting, and the next desk load tries again. After three claimed attempts, Aluna stops trying.

Why the seed picks the shade

The model used to pick each colour from a different list of eight named colours, sky among them. It gave the same kind of prompt the same colour, and the name "sky" read as a backdrop: three of the first four live logos stood on sky blue. The family is still the model's pick and can repeat. Because of the seed, capabilities that name the same family usually come out in different shades.

Endings

Activation is the ending that puts a version live. Every other ending leaves the desk without Books. A first build can fail at a stage before the commit. It is cancelled when you cancel, when you leave while it builds or when the browser disconnects. Only one build runs at a time, so a build can wait for another to finish before it starts. A build is refused as stale when the catalog changed after the resolver read it, for example because the build ahead of it made or changed a capability. A running build is interrupted when the process dies; a build still waiting has no metrics row yet, so nothing is left to mark.

The events the window acts on

The server streams a build's events to the window over one server-sent events connection. The same stream carries the Developer panel's previews of what each stage produced, such as the spec, the units and the Gate's verdict.

narration
A line in Aluna's voice, added to what she has already said, and at an ending, its Continue button
fragment
HTML placed by its marker or out of band: a window title, the provisional tile and its name, a notice in the prompt bar or the screen the build displaced
commit
The live version's collection and its tile, replacing the window's contents, sent only for an activation
done
The end of the build: the server ends the stream and the client closes its side
heartbeat
A keep-alive with no id, meaning nothing to the product

A browser's EventSource reconnects by itself when a server closes the stream, so the client declares sse-close="done" and closes the connection itself at the last event. Without that, the build never ends in the browser: the provisional tile stays on the desk, the prompt bar stays locked and the browser keeps reconnecting to a build that no longer exists and gets another done each time.

The route

Your save is a POST to /capability/books/create. read and search are GET, and create, update and delete are POST. Any other pairing gets a 404 before any generated code is loaded.

The router's own form fields, such as the one listing which fields the form sent, start with __aluna_. It takes them out of the form before the handler sees it, and refuses any other key with that prefix. A spec cannot name a field with that prefix.

How generated code writes and reads

Generated code can damage your data only by writing to it, for example by dropping a table or corrupting a row. A read cannot lose data. Generated code gets no SQL that changes data and no table name to write to, only a write interface the platform hands it. For reads it composes its own SQL, one statement at a time. Books declares no read of another capability, so that SQL reads only Books' table.

What the handler is given

The create handler receives the parsed form and three interfaces: one to query, one to present records as cards and one to write. It never sees the raw request. Its write interface is bound to Books, with no table name and no way to pick another capability. In the Gate, each handler gets the interfaces a live request would give it, built over a throwaway database.

For update and delete, the router checks that the request names exactly one record, and binds the write interface to that record before generated code runs. The handler is never handed the record's id: update takes only the values to write, and delete takes nothing. No handler can change a book the request did not name.

What a handler may write

Through a write interface bound to Books, and for update and delete bound to the one record the request named.

  • The platform normalises values, enforces required fields and validates the finished row
  • Update merges into the stored row: fields the form did not send survive an edit, and so do the platform's id and created_at columns
  • An optional field can be cleared with a null or an empty value; a required field cannot be cleared
  • A handler that returns one of its declared errors has its write rolled back

What a handler may read

SQL the handler composes itself, on a read-only SQLite connection the platform opened, with values bound as parameters where the handler supplies them.

  • Every query declares the columns it expects, and the platform discards any other column in the result
  • A query that asks for records returns their ids in order, and the platform loads the real rows in the same read transaction, so every card belongs to a stored row

A save with no title never reaches cap_books. The browser stops an empty title first, with the platform's line I still need this one. A title of only spaces gets past the browser, and then the create handler has to catch it. It checks for missing required fields before it writes, and when one is missing it returns its declared missing_required_fields error, in words the model chose. If a blank value slips past the handler, the write interface refuses it in the platform's words. On update, the write interface's check of the merged row finds the missing field, and the handler turns that failure into the same declared error.

What the platform draws

Platform code draws the collection with its search box and its button for a new record, the empty state, the wrapper that makes a record pressable, the record view, every field control and the delete confirmation. Besides the spec's words, such as field labels, the model writes two things that reach Books' screens. The item renderer turns one record into the markup inside its card. The HTML a handler returns puts those cards together and adds small pieces of its own, such as echoing a search. The enforcer from chapter three limits a record's markup, and the platform strips scripts and event attributes from all the HTML a handler returns.

The catalog lists each field with a name, a type and a lifecycle, and lists an active list field's input style too. active means the field is on the form. A later change can take a field off the form and keep its values, which Aluna calls hiding it, and a hidden field is listed as lifecycle inactive.

Books appears a second time in the prompt, as the capability open in the window, and the prompt tells the model that the open capability is strong context for a change that names nothing. Your sentence names no capability, so the resolver targets Books and classifies the sentence as extend_capability. A change to a capability that already exists is an evolution.

Had you typed show the page count on each card, the resolver would have classified it as ui_change: a change to how Books looks or what it calls things, limited to the closed list below. The builder runs the same steps for both, and fails a ui_change whose new spec changes anything outside that list, such as adding or hiding a field or reordering the form. A request about how something looks that falls outside that list, such as moving it 2px or making it blue, is classified as reject, because Aluna chooses colour, size, spacing and position herself. A request for a new look for the card can be a ui_change, because the card's design direction is on the list; the model then picks the design tokens.

Everything a ui_change may change

The capability's name, the word for one record, field labels, a list field's input style, a text field's multi-line box, the hint under a field, the layout and the card: its design direction and the fields it shows.

A whole new spec

The builder asks the model for a complete candidate spec: Books as it should be once the change is made, every field included. The platform validates it before any schema change or code. Then the Diff Engine compares the candidate with the committed spec, and each difference becomes a typed change fact. Here there is one: a new field, finished, of type date.

A complete candidate

A patch would list only what the model thinks changed, and everything it left out would be trusted to be unaffected. With a complete candidate, deterministic code decides what changed.

The matrix

The Diff Engine looks each change fact up in the matrix, a table with one row for each kind of change the engine can name. The fact's row adds work to the plan: platform work, units the model writes again and test suites. A suite is one Action's behavioral tests. Each unit the plan does not select is copied into the new version byte for byte, the same file that passed the Gate for the previous version. When the candidate changes nothing

If the candidate means exactly what is already committed, the evolution ends without a new version, and Books stays at v1. The build's metrics row shows a success with the outcome no_change, and the model call that produced the candidate is still measured. The window holds Aluna's line until you press Continue: That's already exactly how this works — nothing to change.

Rules the matrix keeps

A fact can add work to the plan and never remove any, so a combination of facts never does less work than one of them needed alone. A unit is copied only after every difference has been accounted for and none of them selected it.

When the engine meets a difference the matrix has no row for, the build stops before anything is published, and its metrics row shows a failure. A new kind of change to the spec cannot skip the work it needs: the engine will not go on until someone has written that work into the matrix.

The plan is fixed before any unit is written, and only a Gate repair can later rewrite a unit the plan did not select.

The old code in the prompt

A selected unit is written with its old source in its prompt, as context the model may use, and a copied unit never enters a prompt. Before the old source goes in, deterministic checks confirm that it still meets the unit's contract and names no hidden field and no table outside its scope, not even in a comment. A name left in the old source would bring that field or table back into the prompt. When the checks fail, the unit is written again without its old source.

A copied unit keeps working beside a new column. Every query declares the columns it expects and the platform discards the rest, so SELECT * cannot leak a new field into code written before the field existed.

Which tests run

A suite's inputs are the parts of the spec its tests were written from: the behavior prose, plus the part of the schema its Action works with, the errors that Action declares and any capabilities that Action reads. A suite whose inputs changed is written again, and a suite written again always runs. A suite whose inputs did not change can be carried into the new version byte for byte. A carried suite runs when its handler was written again or repaired, and is skipped when its handler was copied.

When a suite is carried, and when every suite runs

A suite is carried when the committed version had the behavioral rung on, its inputs are unchanged and none of its cases names a field that is now hidden. The field list used to fill in sample books is not one of the inputs. Every suite runs when the behavior prose changed, since prose cannot be tied to one Action. They also all run when the item renderer changed along with a handler, when design lint repaired the renderer or when the fields the card may show changed.

For add the date I finished, the candidate leaves the card as it was. The plan adds a nullable column and puts the field on the form and the record view. It sends create and update back to the model, and copies read, delete, search and the item renderer. The Gate passes, and Books v2 goes live.

What an evolution cannot change

The platform refuses these changes before any code is written. An evolution cannot drop a field or change a field's name or type, because copied code was written against them. It cannot remove a committed choice option or change the value the option stores, because stored records hold that value. A choice field can sort its options under headed groups, and an evolution can reword a heading but cannot change a group's id. An evolution cannot change the capability's id, because Books' address and table are named after it. It cannot change the subject or hue families the logo was drawn from, because Books keeps the logo it was first drawn with. A hidden field stays exactly as it was until it is made active again, and an active field's label can change.

Inside a version

Each build that changes the spec makes a new version, and each version is a complete, immutable directory on disk. It holds the exact spec, all five handlers, the item renderer, the frozen tests when the behavioral rung was on and a manifest with a digest for every other file. A version can be verified before it goes live. An old version holds a whole capability by itself.

The registry points at the one live version, which supplies the old source and the carried tests for the next evolution. Nothing serves an older version, and the older ones stay on disk as committed history. A committed version that goes missing is treated as corruption.

Outside a deletion, the only version directories Aluna removes are ones whose metrics rows prove they never went live. She removes them at start-up, when a later new capability's build starts or when a later evolution is about to publish. Removing a version that did go live would first need a durable log of every activation, which Aluna does not keep yet.

Illustrative. The real classification comes from a model call against your own catalog, and the same sentence can land differently on a different desk.

Overlaps

Before it classifies a sentence, the resolver reads every capability's prompt_context. When a new request overlaps something that already exists, the model settles it: evolve the existing capability, or start a separate one. For a separate capability, the platform refuses a name already on the desk and a numbered copy of one, such as books_2 or Books 2.

Aluna accepts an occasional wrong resolution so that she never stops to ask you.

Capabilities that read each other

Each capability has an isolated table, with no foreign keys, and two capabilities never share a field. A capability that needs another one's data declares, for each Action, which capabilities it reads. That Action's SQL joins the tables when it runs, and the platform checks every query against the declaration.

In the Gate, the throwaway database gets an empty table for each capability the spec reads. When the capabilities an Action reads change, the model writes that Action's handler and test suite again and the platform updates its declared reads. Nothing else changes. If a capability hides a field that another one reads, the column stays. The capability that reads the field keeps working and none of its units is written again. Waiting, then the recheck

Builds and platform writes wait for the lease in a first-in, first-out queue. A waiting build has no time limit. It leaves the queue when it gets the lease, when you cancel or when the browser disconnects. Once it has the lease, a build holds it for up to four hours. When that expires, the coordinator tells the build to stop, and the build keeps the lease until it has stopped.

At the front, before any model work, a build rechecks what it was classified against. An evolution checks that its capability still exists as the same capability at the same version. It then checks the catalog fingerprint, a hash of the catalog that the platform stamped on its classification. The fingerprint covers every capability row apart from its logo: logos arrive whenever an attempt finishes, and counting them would make a build stale over a drawing. A change to anything else in any row moves the fingerprint, and a queued build is refused even when the change that landed was about another capability.

A build that fails the recheck is refused as stale. Aluna does not reclassify it: against a different catalog, the resolver may read the same sentence as a different request. A stale build never starts: it makes no model call of its own and touches no file.

How a new capability rechecks

A new capability checks only the fingerprint. A separate capability proposed to settle an overlap first checks that its id is still free, then the fingerprint.

When a save is refused

A save needs the lease too: a record write runs its whole handler inside one transaction on it, and a declared error rolls the write back before the lease is let go. A save that joined the queue could wait for hours, behind every build ahead of it. A record write never joins it: while any writer holds the lease or waits for it, the write is refused at once, and you save again later.

The open capability

An open capability reaches the loop only when the resolver reads a question as leaning on it, as how many did I add today? does. The resolver then names the open capability as the question's target. The target tells the loop what vague words point at and never limits what the loop may read. Your Le Guin question names what it is about, so the resolver sets no target and the loop is not told that Books is open.

Why a loop

The model gets one tool, a parameterised read-only query, and decides for itself what to run next, up to ten times. A fixed pipeline was rejected: it would need a branch for each case the loop already handles, such as a malformed query, an unknown column or an empty result. The model is told to report only figures a query returned or values it searched on, because a model counting rows will eventually miscount one.

When little or nothing matched

You started Books this year. Ask how many books you finished last year, and the only read returns a count of zero. A model phrasing that zero could say You didn't finish any books last year, a claim about your life when the only fact is an empty result. When the only figures a step returns are what SQL gives back for no rows at all, such as a count of zero, Aluna treats the step as matching nothing. A value alone cannot say where it came from, so she reads the statement's query plan first: a statement that could produce a figure over no rows by itself, through a literal, a bound value or arithmetic, counts as matching nothing whatever it returned.

Narration and the answer

While the loop runs, Aluna narrates in lines the platform wrote. Each step carries one of six labels (naming, counting, totalling, listing, dates or other), and each label has one fixed line. The model can neither narrate in words of its own nor put SQL on the screen. The answer itself arrives as prose, with bullets only where a line would have been a list.

Values that mean the same thing

The model works out which stored values mean the same thing by reading the data. A choice field's options are in the prompt, and a naming step reads the distinct values of any other field, whole lists for a list field. Embeddings were declined. They would add a fourth derived artefact beside the handlers, the item renderer and the tests, with its own version key, its own recovery and a model call every time a record is written.

How a question is kept small and read-only

A question reads only active fields. A step's result may be at most 16 KiB, and a statement whose text and bound values already exceed 16 KiB is refused before it runs. A read that would take the question past 64 KiB is refused too, well under what ten full steps would add up to. Anything over a limit is refused and never truncated, and the refusal goes back to the model as a failed step, which uses up one of its ten.

SQLite calls on the server's main thread are synchronous: one slow query there would stall every request until it finished. The loop's queries run in a worker with its own read-only connection instead, which keeps the server answering. Terminating that worker hands control back at once, but the statement keeps running until SQLite finishes it. Stopping the statement itself would need sqlite3_interrupt through FFI, and Aluna does not call it.

A question is cancelled when you send anything else from the prompt bar, when you dismiss the answer or when the browser disconnects. Each model call in the loop has a five-minute limit.

Opening the connection read-only

Necessary, and not enough on its own. A read-only connection can still write a copy of the database elsewhere with VACUUM INTO, attach other files and spill temporary tables to disk.

Not sufficient

One statement, checked first

On the main thread, the check requires a single statement starting with SELECT or WITH, with nothing after a semicolon, that reads only this question's capabilities. The check looks only at what a statement reads, so a WITH that writes gets through when it reads nothing outside them. A statement starting with INSERT, UPDATE, DELETE or REPLACE skips the check by name. Both are left on purpose to the worker's read-only connection, which refuses them.

Bounds reads

PRAGMA query_only = ON

Refuses VACUUM INTO and temporary tables.

Load-bearing

Six statement forms refused by name

Inside the worker, ATTACH, DETACH, PRAGMA, VACUUM, REINDEX and ANALYZE are refused before they run, and so is any second statement in the same string. Of the checks inside the worker, only this one stops ATTACH.

Load-bearing

Temporary storage kept in memory

Moves SQLite's temporary storage off the disk. It sets no size limit, and it guards what query_only already refuses.

A second guard

Bun's SQLite binding exposes no authorizer callback: nothing inspects a statement as SQLite compiles it. The read-only connection, query_only and the name check are the whole defence against a question writing.

After a question

Refusals, timing and retries

A deletion is refused when another write holds or waits for the lease, when a capability declares a read of this one, when the reads still running do not stop within fifteen seconds or when the deletion is stale: the capability was deleted and built again while the confirmation stood open. A deletion that fails before the commit ends the same way. The refusal replaces the confirmation with a line and a Continue button, and by then reads of the capability are allowed again. Continue takes the same route as the confirmation's Keep it button. A capability that is already gone gets one line and no Continue.

After a successful commit nothing waits for Continue: the tile is gone, the prompt bar says the capability was deleted permanently and the window either puts itself away or gives back whatever the confirmation covered. A clean-up that fails retries up to three times over roughly the next forty seconds. After that, every start-up runs it and every desk load schedules it, until it finishes.
